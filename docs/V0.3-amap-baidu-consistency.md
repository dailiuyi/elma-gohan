# LowRegret V0.3：高德 + 百度跨平台一致性

## 版本与边界

- 应用版本：`0.3.2`（V0.3.2 增加高德餐饮身份验证与分类可信度降权）
- 风险算法：`risk-v0.3`
- 推荐算法：`recommendation-v0.3.2`
- 主 POI：高德；第二 Evidence：百度 Place
- 保留：File Evidence、TasteProfile、品类筛选、最多 6 家候选与 5 次 reroll
- 默认链路不包含：Web Search、抖音、美团/点评非公开接口、爬虫、价格冲突风险、逐餐厅详情请求

用户主动触发的公开 Web Search 弱线索链路见 [`V0.3.1-on-demand-deep-evidence.md`](V0.3.1-on-demand-deep-evidence.md)，它不参与本页描述的推荐排序。

百度接口字段参考官方 [地点检索 3.0](https://lbs.baidu.com/faq/api?title=webapi%2Fguide%2Fwebservice-placeapiV3%2FinterfaceDocumentV3)；V2 只作为细评分的可选补充。所有平台字段都允许缺失，缺失值不转换为零。

## 当前数据流

```text
高德周边餐厅（Restaurant 主实体）
→ 硬过滤
→ 读取 external_entity_mapping 缓存
→ 对未覆盖候选发起百度 Place V3 第 0 页圆形检索
→ total 大于单页容量且仍有 NO_MATCH 时，自适应追加 V3 第 1 页
→ 合并两页并按百度 UID 去重，重新执行 EntityResolver 一对一匹配
→ 对剩余 NO_MATCH 按完整归一化店名、品牌短名、suggestion 的顺序逐店补召回
→ 未使用第二页和逐店补召回时，已匹配但缺细评分最多追加 1 次 V2 圆形检索
→ CrossPlatformConsistency
→ risk-v0.3
→ HIGH 风险剔除
→ recommendation-v0.3.2 + 分类可信度 + TasteProfile
→ Top-10 多样化 + 有限加权随机
→ 冻结最多 6 家候选及 Evidence 摘要
→ 首次推荐 / 最多 5 次 reroll
```

百度不可用、无结果、无匹配、匹配歧义或字段缺失时，高德候选仍继续进入 RiskEngine；系统不把“没有百度数据”解释成餐厅存在平台冲突。

## 平台 Evidence

`PlatformEvidence` 是平台无关模型，包含来源、观测时间、名称、地址、GCJ-02 坐标、综合/口味/服务/环境评分、评论数、人均、营业时间、品牌和电话。百度原始 `JsonNode` 只存在于 `BaiduPlaceApiProvider` 内，不进入匹配、风险或 API 层。

百度每次新推荐：

1. V3 `/place/v3/around` 先召回第 0 页（`query=餐饮`）。
2. `total` 大于单页容量且仍有未匹配候选时，优先读取 `query=餐饮` 第 1 页；逐店搜索不能替代这次通用分页。
3. 合并通用两页、按百度 UID 去重并重新匹配后，对剩余门店按距离逐家补召回。每家先用保留商场/分店信息的完整归一化店名调用 `/place/v3/around`，再用去业态后缀的品牌短名调用；两者去重且至少两个字符。最后才以品牌短名调用 `/place/v2/suggestion` 兜底。
4. 逐店 `/place/v3/around` 默认以高德门店坐标为中心、半径 500m、`radius_limit=true`，并使用餐饮行业的距离升序过滤参数。
5. 默认最多处理 10 家未匹配门店、最多发起 20 次逐店补召回请求；包含通用页和可选 V2 在内，整次百度召回最多 22 次调用且时间预算为 8000ms。
6. 未使用第二页和逐店补召回且已匹配对象缺少细评分时，才追加 V2 `/place/v2/search`。

所有百度 Place 入口共享同一个进程级平滑限速器，默认每秒最多发放 3 个许可；单次请求最多等待 1000ms。等待超时返回 `UNAVAILABLE`，不得形成有效 `NO_MATCH` 负缓存。该限制覆盖 V3 通用分页、逐店 nearby、region、suggestion 和 V2；如果未来扩为多实例部署，需要再增加跨实例的分布式限速。

固定参数为 `coord_type=2`、`ret_coordtype=gcj02ll`、`scope=2`、`radius_limit=true`、`page_size=20`；V3 通用页码只使用 `0/1`，V2 固定第 0 页。连接/读取超时默认为 1500/2500ms；HTTP 或业务状态异常不重试。V3 第 1 页失败、逐店调用失败、时间/次数预算耗尽或门店因额度未处理时，相关 `NO_MATCH` 不形成有效负缓存，下次推荐允许重新查询。日志记录调用数、完整处理门店 ID、跳过门店 ID、截断状态和平台不可用状态。

## Entity Resolution

匹配分：

```text
45% nameSimilarity
+ 30% coordinateSimilarity
+ 15% addressSimilarity
+ 10% telephoneSimilarity
```

- 名称先去掉括号分店名、停业标记、门店后缀和业态后缀（餐厅/湘菜馆/家菜馆/披萨速递等），再算 bigram Jaccard；品牌名相同视为 1.0，较长名称包含另一侧品牌名时不低于 0.85。80 米内同品牌前缀或改名店直接收下。
- 地址做 NFKC 和字符 bigram Jaccard。
- 电话按数字归一化；相同电话可为 300m 外同名门店提供强保护。
- 坐标距离 `≤30m` 为强匹配，30～100m 线性降到中等，100～300m 线性降到零；超过 300m 默认拒绝。
- 接受阈值 `0.50`。覆盖优先时不再因分差过近标成 `AMBIGUOUS`，取最高分候选。
- 近距离尽量收下：≤40m 且名称 ≥0.20、或 ≤80m 且名称 ≥0.40，直接抬到可接受分数。
- 同批执行一对一占用，一个百度 UID 只能匹配一家高德餐厅；当前不做二分图重分配，冲突日志记录冲突数、因此变成 `NO_MATCH` 的数量及是否存在可接受的第二候选。
- 地址或电话不可比较时按实际可用字段重新归一化；200m 内且名称相似度至少 `0.20` 时优先保留，否则稀疏证据需满足名称相似度至少 `0.40` 且距离不超过 `150m`。

缓存 TTL：`MATCHED=30天`、`AMBIGUOUS=6小时`、完整召回后的 `NO_MATCH=30分钟`，`UNAVAILABLE` 或召回不完整的 `NO_MATCH` 立即过期；V3 Evidence=6小时、V2 细评分=24小时。完整缓存覆盖时不调用百度；reroll 使用会话创建时冻结的证据，不重新检索。

## risk-v0.3

六项因子与默认权重：

| 因子 | 权重 | 来源 |
| --- | ---: | --- |
| `ratingRisk` | 20% | 两平台均有综合评分时等权平均，否则用单平台评分 |
| `templateRisk` | 15% | File Evidence 评论模板比例 |
| `burstRisk` | 10% | File Evidence 评论时间集中度 |
| `trendRisk` | 10% | File Evidence 近期评分趋势 |
| `dataInsufficientRisk` | 25% | 平台不可用、未匹配及字段缺失 |
| `crossPlatformConflictRisk` | 20% | 匹配成功后的综合评分绝对差 |

评分差映射：`≤0.2 → 0`，`0.2～0.7 → 0～60`，`0.7～1.0 → 60～100`，`≥1.0 → 100`。方向只影响用户理由，不影响风险值。例如高德 4.9、百度 4.2 的差值为 0.7，冲突因子为 60，对总风险贡献约 12 分。

数据不足默认增量：百度不可用 `+30`、无匹配或歧义 `+25`、匹配但百度综合评分缺失 `+15`、高德评分缺失 `+20`、两平台评论数均缺失 `+10`、价格均缺失 `+5`、营业时间均缺失 `+5`，最终限制在 0～100。

`MATCHED` 时置信度为 `35% 高德完整度 + 35% 百度完整度 + 30% 匹配置信度`；未匹配/不可用时为 `50% × 高德完整度` 且最高 0.5。评分冲突本身不降低 confidence，因为它可能是高可信的冲突结论。

全部阈值集中在：

- `elma.baidu.*`：开关、地址、批量参数与超时
- `elma.entity-resolution.*`：匹配权重、阈值与 TTL
- `elma.risk.*`：风险阈值、数据不足增量、权重、等级和版本

## API 与持久化

`RecommendationResponse` 新增可选 `evidenceSummary`，V0.3 正常链路始终返回。客户端可看到匹配状态、匹配置信度、平台标准化评分和一致性说明；不会看到百度 UID、高德 POI ID、原始响应、电话、内部匹配特征或 AK。

Flyway `V3__cross_platform_evidence.sql`：

- `restaurant.telephone`：实体匹配用，不对客户端公开。
- `external_entity_mapping`：保存实体映射、匹配特征、V3/V2 标准化 Evidence、观测时间和过期时间。
- `risk_result.evidence_summary_json`：风险结果的证据摘要快照。
- `recommendation_candidate.evidence_summary_json`：候选池证据摘要快照，确保 reroll 可重复。

## 扩展点与已知限制

- 新平台实现 `PlatformEvidenceProvider` 并映射 `PlatformEvidence` 即可复用实体匹配和风险模型。
- `EntityResolver` 与 `CrossPlatformConsistencyAnalyzer` 均为可替换的独立组件。
- 百度通用检索自适应读取前两页、最多 40 条，再在总预算内逐店补召回；更深分页仍可能漏召回，因此完整召回后的 `NO_MATCH` 也只短期缓存且文案保持中性。
- 当前请求内同步调用百度；未来若真实流量上升，可在不改变领域模型的前提下增加批量缓存、指标和熔断。
- 本期只校准综合评分冲突；价格差异只展示/留存，尚未进入风险。
