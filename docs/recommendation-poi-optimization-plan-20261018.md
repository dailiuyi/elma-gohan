## 结论与边界

建议分两阶段重构：先修百度调用和推荐事务边界，再验证并收敛算法。保留现有模块化单体与 PostgreSQL，不因每秒几次调用引入新的消息系统。

用户确认百度侧额度为 3。控制台该指标究竟是 QPS（每秒请求数）、同时在途请求数，及其按 AK、服务还是账号共享，尚未核对。方案同时限制速率与在途数量，但不会把“3”当成三个线程即可解决的问题。

当前源码已有同数据库跨实例串行通道、最小 400ms 请求间隔、查询缓存、持久化补数队列、401 冷却和 302 日配额停止。因此线上超限还要核对发布版本、实际配置及开发/生产/其他程序是否共享额度；尚未读取生产日志或控制台，不能宣称已定位线上唯一根因。

## 阶段一：稳定百度调用和推荐服务

### 1. 核对额度范围并统一出口

实施前核对线上构建标识、V10 迁移状态、脱敏错误码、实际速率设置和共用额度的调用方。只记录配置别名或指纹，不输出 AK。百度地图 Place 与千帆 AI 搜索分别核对，不能因名称都有百度就假定共用同一配额。

所有消耗同一额度的 Place V2/V3、逐店、区域、suggestion 调用进入一个调度入口；现有同数据库协调继续保留。若开发和生产用不同数据库却共用额度，需要统一经过同一出口或分配明确的子预算，不能各自按 3 发请求。

建议初始工程参数为平滑 2 QPS、最大在途 1、禁止突发。这是留余量的起始配置，不是百度官方限额，也不是已测出的最优值。每次真实 HTTP 请求、分页与重试都消耗同一预算。核对额度定义后再提高利用率。

区分 HTTP 状态和 JSON 业务状态。官方说明：401/402 为并发超限，302 为当天额度耗尽，301 为永久额度耗尽。处理规则：

- 401/402：共享冷却状态；冷却结束只允许一个探测请求，成功后恢复节奏；退避带抖动且受任务总预算限制。
- 302：停止该额度域请求至已确认的日配额重置点，沿用北京时间次日零点策略前核对适用规则。
- 301、鉴权及权限错误：记录可操作原因并停止自动重试，等待配置或额度变更。
- 网络暂时失败和 HTTP 5xx：有限重试；前台截止时间耗尽后交给后台任务，后台重试也重新取得许可。

### 2. 等待外部服务时释放业务连接

将创建流程拆成：短读取 → 无事务的召回/证据/计算 → 短写事务。写事务负责餐厅、风险、推荐日志、候选和行为一致提交；影子任务继续 after-commit 调度。映射缓存作为共享采集数据独立短事务写入。

把当前“每个调用者持数据库连接轮询锁”的等待方式移到有界调度队列。沿用 PostgreSQL 做跨实例协调；只有实际出站执行者持有必要的协调连接，等待者不占业务池连接。协调连接数量固定并与业务池隔离；不得简单删除跨实例锁后只靠 JVM 限流。

前台与后台共用同一配额，调度优先处理尚未过期的前台查询，同时为后台保留进度机会。相同查询合并为一次在途任务，等待者复用结果；一个等待者超时不能取消其他等待者或后台所需任务。

借连接、SQL、排队及 HTTP 都纳入明确的阶段预算，超时后不再开启下一次外部请求。复用一个 HTTP 客户端，使用每请求超时控制，不为每次请求新建连接池。

拆分时顺带处理创建会话真实会触及的竞争：`upsertRestaurant` 当前是查后保存，首次并发创建同一家门店可撞 `(source, source_poi_id)` 唯一键，改为数据库原子 upsert。此处和已经原子化的外部映射不是同一张表。

### 3. 保持补数能力，减少无效调用

保留前台限时取证、后台完整补数和冻结会话语义。命中有效映射直接使用；未命中才申请前台预算。超时后按现有高德可用证据生成推荐并说明百度证据不足，补数服务后续推荐，不修改已经展示的会话。

查询缓存、门店映射、在途请求分别去重。后台任务合并相同门店的未完成工作，保存进度，避免多个相近候选集合重复从头补数。共享原始 POI 或证据，不共享用户的 Taste、历史扣分及最终推荐结果。

首轮不直接对坐标粗粒度取整扩缓存命中，避免改变半径边缘的召回范围；空间缓存优化另需覆盖边界和距离重算测试。

明确“召回未完成”与“完成但无匹配/有歧义”。所有不完整非匹配结果均不得成为有效负缓存；写入保护和任务完成判断同步使用完整性标记。保留完整召回后的正常歧义缓存，避免反复浪费配额。

队列容量若继续承诺硬上限，使用独立短事务锁串行化容量检查与入队；返回 `ENQUEUED / DUPLICATE / FULL` 并记录计数。保留现有租约和跨实例单消费者，不为了增加术语另加一套领取机制。

### 4. 可观测性与容量解释

记录原始业务码、内部失败原因、真实出站次数、速率等待、队列等待、连接池等待、在途峰值、缓存命中、任务年龄、重试/拒绝数量。日志不含密钥或完整带密钥 URL；指标标签不用门店 ID 等无限增长的值。

容量估算：若前台冷请求都需要两次百度调用，在 2 QPS 下只能支撑约每秒一个这样的冷请求；后台也要消耗同一配额。后台上限 22 次调用，以 2 QPS 启动最后一次至少需要约 10.5 秒，现有 8 秒预算自然无法每次跑满。这些是理论容量估算，说明必须依赖缓存、合并和可续做任务，不能靠增加线程解决。

## 阶段二：收敛推荐算法

### 1. 先做行为保持的结构整理

推荐编排只承担流程：召回 → 一次硬过滤 → 证据快照 → 风险与偏好特征 → 排序选池 → 持久化。

- `HardFilter` 只在进入评分前执行一次；给引擎明确“已过滤候选”的输入约定。
- 形成一次计算的不可变特征集，让评分、解释、快照复用同一结果；合并重复历史扫描，避免每个候选重复遍历同一份历史。
- 拆分会话写入与响应组装，减少 `RecommendationService` 同时负责网络、领域计算、JSON 和数据库事务的耦合。
- 用固定输入、seed 和时间验证整理前后 v0.4 结果一致；不要在同一个改动里悄悄更换权重。

### 2. 复用 v0.5，验证信息重复计分

继续使用已有 v0.5 shadow（旁路计算，不改变用户响应）作为候选方案，不新增第三套推荐框架。它已有近似并列选择和质量受限多样化，但不能据此断言所有重复影响已消除。

建立特征归属表并逐项消融：

| 信息 | 拟验证的职责 |
| --- | --- |
| 评分及样本量 | 主要表达预期质量；评估是否还需要在风险中重复扣分，明显低质量的准入约束单独保留并验证 |
| 评论异常、平台冲突、近期恶化 | 表达真实风险；不把上游限流本身当成餐厅存在问题 |
| 缺失、过期和匹配可靠性 | 表达不确定性，统一保守处理；检查质量、风险和置信收缩的累计惩罚 |
| 用户偏好 | 按有效反馈量调节强度；保留冷启动和客观风险边界 |
| 近期重复 | 收敛为一个可解释的重复约束/惩罚；与选池多样化的不同职责分开验收 |
| 预算、距离 | 保留当前契约的区间边界；v0.5 的预算满足度、绝对步行距离偏好作为明确策略变化评估 |

v0.4 同组 90/60 分仍可按 60%/40% 抽取，差距较大时随机性过强。优先验证现有 v0.5 的做法：安全准入后在接近最优的候选中随机，再用质量损失受限的多样化选备选。分差和安全阈值用数据校准，不把方案中的示例当发布参数。

保留 `excludeRestaurantId` 在完整价格基线和风险计算之后处理的当前边界；不因优化而破坏快照对照。当前 reroll 不访问百度，也不重新取证，这一点继续保持。动态 reroll 和成对偏好学习尚未服务响应，不纳入首轮稳定性修复。

### 3. 回放与切换门槛

使用已有 V7/V9 快照、固定 seed、冻结时间与配置对照 v0.4/v0.5；缺少完整输入的历史记录不宣称可完整重放。覆盖商场同品牌不同楼层、连锁分店、冷启动、价格缺失、单平台、百度超限、近期重复、稀疏候选及预算边界。

对照首推变化、差候选被抽中概率、无可选率、安全拦截、解释一致性与计算开销；移除一个重复因子后再比较结果，避免同时改权重导致无法归因。

历史行为存在旧策略选择偏差，不能直接把离线命中率当线上接受率。先完成人工风险复核，再在单独获准部署后使用已有稳定分桶灰度，观察接受、reroll、DISLIKE 与尾延迟。上线依据和阈值在取得基线后冻结。

算法切换完成后删除旧实时评分和重复选池代码。历史会话及 API/存储格式属于已有对外契约，继续按原快照读取；历史审计计算不作为另一条在线 fallback 保留。单纯删除 serving 安全闩不构成 v0.5 接线。

## 验收标准与实施次序

建议按四个本地阶段交付，每阶段小结；推送、PR、部署另行授权。

1. **复现及错误分类**：添加 402/301、本地小连接池竞争、歧义缓存不完整和容量最后一位竞争测试，核对线上超限归属后修复错误分类。
2. **调用与事务重构**：一次共享配额调度、排队不持业务连接、短事务、复用 HTTP 客户端、原子餐厅写入和补数进度。保持当前推荐规则及公开接口。
3. **算法整理与回放**：消除重复职责，输出 v0.4/v0.5 对照和消融结果；保留 serving 关闭状态直到接线和质量验收完成。
4. **获准后的灰度与收尾**：固定分桶、人工体验验收、监控，切换后删除旧在线路径并更新文档。

验收全部使用本地 HTTP stub 和隔离 PostgreSQL 起步，不能对额度只有 3 的真实 API 做压力测试：

- 同一查询 50 个并发请求，出站只发生一次，所有未超时等待者复用结果。
- 50 个不同查询验证平滑速率、在途上限、有界排队和拒绝；前台不需要全成功，但超时返回原因必须清楚，不能拖垮推荐数据库。
- 两个独立实例共用调度状态，合计遵守一次额度；401/402 冷却及单探测、302 重置、301 停止均可验证。
- Hikari 小池并发前台/后台，验证等待期间不耗尽业务连接；借连接预算、取消与恢复有断言。
- 999 条队列同时插入不同任务验证容量，重复任务验证去重；任务崩溃、租约到期、部分进度及终止原因可核验。
- 不完整 `NO_MATCH/AMBIGUOUS` 不结束补数、不覆盖新鲜成功映射；完整负缓存正常工作。
- 并发创建相同新门店不产生唯一键错误；reroll 保留会话串行推进和零百度调用。
- 算法结构整理阶段固定输入输出一致；策略调整阶段必须提供可回放的变化清单。

手动验收路径：首次定位推荐 → 连续“下一页” → 修改条件重新推荐 → 百度限流模拟下再次推荐；核对耗时、解释、候选是否重复及证据状态。外观由用户验收。
